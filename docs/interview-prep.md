## 0. 一页速查表

### 三档自我介绍（可直接念）

**30 秒**

> 我做了一个对话式电商 Agent：说一句话走完「搜索 → 推荐 → 对比 → 加购 → 下单」，Agent 的每一步推理实时画在界面上而不是只丢一段文字。两个特点：商品目录是 420 件真实平台抓取样本、不是手编数据；没有 API Key 也能完整跑通——LLM 不可用时自动降级为规则解析加模板回复，而且降级这件事本身写在时间线上，看得见。

**2 分钟**（在上面基础上加四句）

> 技术骨架是 LangGraph 的 StateGraph：9 个节点、6 类意图分流、一个受控的检索细化环，环用计数器封顶 2 轮。我评估过 AgentExecutor 和 tool calling，都刻意没用——工作流是确定的，图本身就是编排层，再叠一层「让模型挑工具」是多余的间接层。记忆我分了四层：会话内历史、会话持久化（SQLite checkpoint）、跨会话结构化画像（localStorage）、语义记忆不做。有两道防线：LLM 输出属于不可信输入，回复进状态前要过落地校验——抽所有金额逐个核对是否来自真实数据，不合就先纠正重试一次、仍不合用模板；流式侧只把面向用户的节点 token 推给前端。工程上 363 个单测（25 个文件）、`tsc` 零错误，首屏 First Load 423 kB。

**5 分钟**（按五段展开，每段绑数字）

> ① **数据**：420 件 = 7 品类各 60，来自两个公开的真实抓取样本；每件商品我都标了字段真实性——销量只有 88/420 是真字段，其余记 0 并改展示评价数；库存件数是派生的，所以界面只显示等级不显示件数。
> ② **编排**：StateGraph 9 节点，条件边声明式；`enrichLiveData` 是搜索引擎之后的**条件触发补充节点**（六条判定全满足才进），默认源下第 4 条自然失败，所以零行为变化。
> ③ **记忆**：四层的作用范围不同，介质也就不同——prompt 上下文 / 图状态落盘 / 浏览器本地；第四层语义记忆不做，理由写在 ADR 里（不是「RAG 不好」，是在这个项目里不成立）。
> ④ **防线**：落地校验拦下过模型自己算的合计 ¥2749；实时数据失败完全静默、只在时间线留一条中性记录；序列化失败保留上一版产物（原子写盘）。
> ⑤ **工程纪律**：11 条 ADR 每条都写代价；25 个已知问题逐条标「已修 / 决定不改 / 边界」；每个数字在文档里都留出处，区分实测、推断、未验证。

### 最可能被问的 10 个问题（一句话答案）

| # | 问题 | 一句话答案 |
| --- | --- | --- |
| 1 | 为什么用 LangGraph 而不是手写循环 / AgentExecutor | 我的流程是确定的九节点图，需要状态合并、可持久化中断和结构化事件流——这三件事 StateGraph 直接给，自研要自己写一遍；AgentExecutor 是黑盒循环，中间过程既不可控也不可视。 |
| 2 | 图里有环吗？怎么收敛？ | 只有一个环 `refineSearch ⇄ searchProducts`，用 `refineCount < 2` 封顶；不封顶就会一直「放宽 → 仍为空」绕到 LangGraph 抛 `GraphRecursionError`。 |
| 3 | 为什么不用 tool calling | tool calling 解决的是「运行时动态选择未知工具集」，我这里工具与节点几乎一一对应、路由只有 6 类——这个问题不存在；`tool()` 契约写好后我评估并删掉了，保留 zod schema 做入参校验。 |
| 4 | 状态字段怎么设计的？实时数据为什么不写回 `searchResults` | 17 个字段、每字段声明 reducer（追加 / 浅合并 / 合并 / 覆盖）；实时值单独放 `liveOverrides`，否则就再也说不清哪个价格来自快照、哪个来自实时查询——「数据可追溯」要做成结构上的事实。 |
| 5 | interrupt + checkpointer 怎么实现的？ | `prepareOrder` 里 `interrupt()` 抛中断、checkpointer 落一次盘、前端弹窗确认后 `Command({ resume })` 恢复；节点会重入两次，所以订单号用 `thread_id + messages.length + 购物车` 做 seed 确定性生成。 |
| 6 | 记忆为什么分四层？第四层为什么不做 | 按作用范围分层，各层用最合适的介质；第四层不做是因为 420 件结构化商品用「关键词 + 标签 + 排序」已够用，引 embedding 会破坏「没有 Key 也能跑」这条基线。 |
| 7 | 画像为什么存 localStorage 而不是服务端 | 没有账号体系，服务端存了也无法归属；存本地天然与 `sessionId` 解耦，「新会话」不会清掉偏好；服务端只在请求期内经 `config.configurable` 用一次，用完即弃。 |
| 8 | 为什么要做落地校验？抓到过什么 | 它拦下过模型自己算的两件合计 ¥2749（数据里没有这个数），还拦过「截断的万口径」和「把评价数写成销量」；处理是先纠正重试一次、仍不过才降级模板。 |
| 9 | 三级降级是什么？无 Key 能跑通哪些 | 结构化输出三级（function calling → jsonMode → 纯文本 JSON + zod）、意图两级（LLM → 规则）、回复两级（LLM 流式 → 模板）；无 Key 时搜索 / 细化 / 对比 / 加购 / 结算中断恢复 / 跨会话画像全部可用，彩排四步实跑通过。 |
| 10 | 上生产你会先补什么 | 先补三件：会话鉴权 + 限流 + 单次 token 上限；checkpointer 换 PostgresSaver + 独立定时清理；数据更新从手动命令改成定时任务。然后是画像出境合规与 E2E 回归。 |

### Q1 · 为什么用 LangGraph 而不是手写循环 / 不用 AgentExecutor `概率：高`

**一句话答案**
> 我这个系统是「流程已知」的：九类节点、六类路由，难点在状态合并、可中断与可持久化、以及把过程画出来。StateGraph 这三件事都是现成的；AgentExecutor 是黑盒循环、中间不可控也不可视，自己写状态机则要把这三件事重写一遍。

**展开讲法**
> 我评估的其实是三条路：AgentExecutor、自研 while + 状态机、StateGraph。选 StateGraph 的理由不是「流行」，是三个具体缺口：① 状态合并——我 17 个字段里 `messages` 要追加、`searchFilters` 要浅合并、`liveOverrides` 要合并而不是覆盖，reducer 机制直接声明，自研就得自己处理并发写入与合并语义；② human-in-the-loop——下单前必须人工确认，`interrupt` + checkpointer 让「暂停、落盘、恢复」是三行代码，自研要自己存「待确认订单」并处理崩溃恢复；③ 可视化——右栏时间线要的是 `node_start / node_end` 这种结构化事件，`streamEvents` 直接产出，自研只能自己埋点。代价我也认：多了一层状态字段与 reducer 的样板，而且必须守「状态写入只发生在节点内」这条纪律。

**证据锚点**
- `lib/agent/graph.ts:65-73`（9 个节点注册）、`:75-89`（6 类意图分流 + 环 + 实时补充分支）
- `lib/agent/state.ts:39-185`（17 个字段与各自 reducer；`mergeLiveOverrides` 在 `:21-26`）
- `docs/decisions.md` 第 1 条（含「如果被追问：循环会不会失控」）
- 数字：9 节点 / 6 类意图 / 17 状态字段 / 环上限 2

**如果被追问**
- *「这不是包装一个 LLM 吗？」* → 图里 LLM 只出现两处、都是结构化输出（`parseIntent` 定意图与条件、`manageCart` 解析购物车指令），其余节点是纯函数；「LLM 说了什么」与「系统做了什么」之间隔着节点代码。

### Q2 · 图里有环吗？怎么收敛？ `概率：高`

**一句话答案**
> 只有一个环：`refineSearch ⇄ searchProducts`——检索为空就放宽条件再来一轮。收敛靠 `refineCount < MAX_REFINE_ROUNDS(2)` 封顶；不加计数器的话，「放宽 → 仍为空」会一直绕，直到撞上 LangGraph 的默认递归上限抛 `GraphRecursionError`，那个报错对用户毫无意义。

**展开讲法**
> 为什么是 2 轮？因为放宽路径只有四条（去标签 → 去关键词 → 放价格 → 去品类），`loosenFilters` 每次至少砍掉一个维度且不回退，两轮足够覆盖大多数空结果场景；再多轮用户已经看不懂「为什么放宽了」。另外我把实时补充节点挂在 `searchProducts → generateReply` 这条直线上，进不进由六条判定决定，**它不构成第二个环**——这是刻意的：再引入一个环就要把「收敛成本」那一套再来一遍，而实时数据只需要一次补充。超限之后不是死路：`generateReply` 会给出可行动建议（放宽预算 / 换品类 / 去掉功能要求）。

**证据锚点**
- `lib/agent/graph.ts:47-52`（`routeAfterSearch`）、`:84`（唯一环的边）、`:85-89`（三分支）、`:92`（补充节点无条件出边）
- `lib/agent/state.ts:175-188`（`refineCount` 注释 + `MAX_REFINE_ROUNDS = 2`）
- `lib/agent/ruleParser.ts:290-298`（`loosenFilters`：每次砍一个维度）
- `lib/agent/nodes/refineSearch.ts:28-34`（主动细化 vs 自动放宽的区分，两者语义不同）
- 数字：环上限 2 / 放宽四条路径

**如果被追问**
- *「你怎么知道它一定收敛？」* → 两层：计数器是硬闸；`loosenFilters` 是单调放宽（去维度后不会自己加回来），所以即使计数放宽，条件也不会来回震荡。`nodes/refineSearch.ts` 的注释里记了另一个反向的坑：曾经「主动细化识别不出相对表述时」无条件落到 `loosenFilters`，把「换成第二件」的关键词丢了、范围从 8 件放宽到 16 件——那次修正是把无条件放宽改成三分支（`8eee844`）。

### Q3 · 为什么不用 tool calling（评估后刻意不采用） `概率：高`

**展开讲法**

**证据锚点**

### Q4 · 状态字段怎么设计的？实时数据为什么不写回 `searchResults`？ `概率：中高`

**一句话答案**
> 17 个字段，每个字段在 `Annotation.Root` 里声明 reducer，合并语义一眼可见：两个追加型（`messages`、`toolCallLog`）、一个浅合并（`searchFilters`）、一个合并型（`liveOverrides`）、其余覆盖型。实时值单独放 `liveOverrides` 而不写回 `searchResults`，否则就再也说不清哪个价格来自快照、哪个来自实时查询——「数据来源可追溯」要做成结构上的事实，而不是靠约定。

**展开讲法**
> 几个具体设计点：① `searchFilters` 用浅合并，所以 refine 只更新变化字段（比如只动价格上限），旧条件不会被清空；② `liveOverrides` 是**合并型**而不是覆盖型——多轮追问会分别覆盖不同商品，覆盖型会让第一轮盖的价在第二轮被整体清掉，界面上的「实时」标注随之消失，而那个价格确实来自真实查询，没理由丢；③ 字段还承担「生命周期界定」的职责：`profilePatch` 由 `parseIntent` 每轮重置为 `[]`、`focusProductId` 消费后写回 `null`（否则同一轮后续 refine 会卡在单件上），这些都是把「每轮开头」当边界的做法；④ `liveFetchedAt` 只有一个用途——条件边的 60 秒冷却。

**证据锚点**
- `lib/agent/state.ts:39-185`；重点 `:59-62`（`searchResults` 覆盖）、`:72-75`（`liveOverrides` + 注释）、`:21-26`（`mergeLiveOverrides`）、`:130-144`（`profilePatch` 生命周期）、`:116-128`（`focusProductId`）、`:175-184`（`refineCount`）

### Q5 · interrupt + checkpointer 怎么实现的？和手写状态机差在哪？ `概率：高`

**一句话答案**
> `prepareOrder` 里调 `interrupt()` 抛出中断信号，LangGraph 落一次 checkpoint 并暂停；前端弹确认弹窗，用户确认后 POST `/api/agent/resume`，用 `Command({ resume })` 恢复，节点**从头重新执行**、这次 `interrupt()` 直接返回用户决策。和手写状态机的差别在于：状态合并、持久化、中断恢复三件事都不在我业务代码里，而我的代价是节点必须写成可重入的。

**展开讲法**
> 可重入带来两个必须处理的坑：① 订单号必须确定性生成——节点会执行两次，用 `Date.now() + 随机数` 会出现「弹窗里一个单号、最终落单另一个」，所以 seed 取 `thread_id + messages.length + 购物车内容`：同一轮两次执行 `messages.length` 相同，跨轮会增长，既保证重入一致、又保证同会话连下两单不撞号；② `interrupt()` 之前的 `return` 会被丢弃，所以订单与金额只能在恢复**之后**才写入 `pendingOrder`。checkpointer 这边：默认 `SqliteSaver`（WAL + `busy_timeout=5000`，dev 热更新残留连接会撞 SQLITE_BUSY），初始化失败自动回落内存态并打印原因——宁可丢持久化，也不能让服务起不来；整个仓库只有 `lib/agent/checkpointer.ts` 一个文件知道后端是什么，8 个节点只依赖 `getCheckpointer()` 与 `threadConfig(sessionId)` 两个函数。

**证据锚点**
- `lib/agent/nodes/prepareOrder.ts:31-40`（seed 三条注释）、`:57-60`（`interrupt` 调用点）
- `app/api/agent/resume/route.ts`（`Command({ resume })`）；`lib/agent/events.ts:112-118`（恢复体契约）
- `lib/agent/checkpointer.ts:42-79`（为什么 `new Database()` 自己开连接、动态 import）、`:81-86`（globalThis 单例）、`:102-104`（`thread_config`）
- `docs/decisions.md` 第 4 条（可替换 checkpointer 的设计与代价）、`docs/architecture.md:43-46`
- 数字：会话 TTL 7 天 / 清理最小间隔 10 分钟

**如果被追问**
- *「为什么挂 `globalThis`？」* → Next.js dev 热更新会重建模块级变量，checkpointer 放模块作用域会让每次热更新丢全部会话；用 Promise 做单例是为了让并发首请求不会各自建一个（异步初始化有竞态）。
- *「SQLite 生产能用吗？」* → 单机 demo 可以；生产换 `PostgresSaver` 只改这一个文件。另外同步 API 会阻塞事件循环、SQLite 文件含完整对话内容必须 gitignore，这两条我都在 ADR 里写了。
- *「TTL 清理怎么触发？」* → 新会话创建时惰性触发 + 10 分钟最小间隔闸门；边界是闸门依赖进程内变量、dev 热更新会重置它（只是多扫一次表，无正确性问题）；生产应改独立定时任务。
- *「和手写状态机比，少了什么自由？」* → 少了「随便在哪写状态」的自由，也少了「自己决定崩溃后恢复到哪一步」的自由；换来的是每次写入都经过 reducer，恢复点由 checkpoint 决定。

### Q6 · 记忆为什么要分四层？第四层为什么不做？ `概率：中`

**一句话答案**
> 按**作用范围**分层，各层用最合适的介质：当前这个 thread 用 prompt 上下文，同一个 sessionId 跨进程重启用图状态落盘，同一浏览器跨会话用 localStorage，第四层语义记忆（RAG）**刻意不做**。第四层不做不是「RAG 不好」，是在这个项目里三条理由都不成立。

**展开讲法**
> 三条理由：① 数据形态——420 件结构化商品（品类 / 品牌 / 价格 / 评分 / 参数 / 标签齐全），偏好用「品类 + 品牌 + 关键词 + 价位」四个字段就能表达，灌进向量库不会优于关键词 + 标签 + 排序，只多一层近似匹配的不确定性；② 基线——embedding 要么再依赖外部 API（多一个 Key、多一份数据出境面），要么引入本地模型（几百 MB 依赖），会破坏「没有 API Key 也能完整跑通」这条我特意保住的性质；③ 表达——这个项目的技术叙事是「用 StateGraph 做显式编排」，再叠一套向量检索 + RAG 管线会让「图在编排什么」变含糊。第三层我做得极简：只有 4 个字段，因为字段越多越难解释每项来源，而「每项偏好都能追溯到一次真实操作」是硬要求。

**证据锚点**

- `docs/decisions.md` 第 3 条、第 6 条

### Q7 · 画像为什么存 localStorage 而不是服务端？ `概率：中`

**一句话答案**
> 因为没有账号体系——服务端存了也无法归属到人。存 localStorage 还顺带解决了另一个问题：它与 `sessionId` **解耦**，所以「开启新会话」不会清掉偏好；服务端只在请求生命周期内用它（随请求上行 → `config.configurable` 注入节点 → 用完即弃），不写 checkpoint、不落任何服务端存储。

**展开讲法**
> 如果按 `sessionId` 存服务端，会立刻违背一条验收标准：「新会话 + 推荐点什么」应当能靠画像落到图书——按会话存的话新会话读不到画像。存浏览器本地就没有这个问题，而且用户能自己清（右栏一键清空，`generation` 自增让在途信号失效）。代价我也说清楚：这是「同一浏览器下的跨会话记忆」，不是跨设备、不是跨用户，清浏览器数据即丢；而且画像摘要会随 prompt 出境到 LLM 服务商，demo 阶段**未做合规处理**，README 里如实标了。边界还有硬上限：最近搜索最多 10 条、单条 ≤ 12 字、品牌名 ≤ 40 字，并在 `/api/agent` 请求边界用 zod 校验，防止被改写的 localStorage 把任意文本塞进 prompt。

### Q8 · 为什么要做「落地校验」？它抓到过什么？ `概率：高`

**一句话答案**
> 因为 LLM 输出属于**不可信输入**——提示词里写「不要编造价格」只是软约束。落地校验把回复里所有 ¥ 金额抽出来逐个核对是否来自真实数据（商品价 / 原价 / 数量小计 / 优惠 / 运费 / 应付 / 两两价差），不合就先带纠正提示重试一次、仍不合改用模板回复。它抓到过一次真事：模型自己算的「前两件合计 ¥2749」——数据里根本没这个数。

**展开讲法**
> 处理是**两级**而不是一刀切：第一版是「不过就降级模板」，但那样用户会明显感觉「它突然不会说话了」；现在先把「哪几个数字不在数据里」点名告诉模型、让它重试一次——关键是**点名**，只说「不要编造」等于把系统提示重复一遍，模型没有可执行的修正目标。重试用 `invoke` 非流式，因为第一段候选的 token 已经流到前端了，重试再流式会让两段候选拼进同一个气泡。校验不止金额：还有一个「万」口径校验（模型自己截断出的 8.4万 会被拦下）和一个**带标签**校验（把评价数写成「销量 8.5万」——数字真实但贴错标签，也要拦）。它和实时数据还有一处联动：覆盖后的实时价必须被登记进「已知金额集合」，否则回复引用实时价会被**自己的校验**判成编造，等于自己把真实数据判成假的。

**证据锚点**
- `lib/agent/grounding.ts:17-28`（三套 pattern）、`:79-87`（`collectProducts` 并入 `liveOverrides` 的注释）、`:140-179`（`checkGrounding`）

### Q9 · 三级降级是什么？没有 API Key 还能跑通哪些？ `概率：高`

**一句话答案**
> 三条链路各自降级：结构化输出三级（function calling → jsonMode → 纯文本 + 手工 JSON + zod）、意图解析两级（LLM → 规则解析器）、回复生成两级（LLM 流式 → 模板）。没有 Key 时搜索、细化、对比、加购、结算（含 interrupt 确认恢复）、跨会话画像提示全部可用——彩排时无 Key 走了检索 / 对比 / 加购 / 结算四步全通，订单号 `ES20260925995029`、实付 ¥180。

**展开讲法**
> 为什么要三级而不是「配好 `response_format` 就行」：实测本项目的 provider 不支持 JSON-Schema 形式的 `response_format`（400），而 `jsonMode` 又要求 prompt 里必须出现 "json" 字样——把可用性赌在某一种 `response_format` 上，换 provider 就会整体挂掉。所以按能力从强到弱逐级降级，任一级成功即返回，全失败才抛错走规则兜底。规则解析器有一个刻意的设计：**词表全部从商品目录派生**（中文 2–4 字 n-gram 集合、标签与品牌词表都从 `PRODUCTS` 来），所以不会出现「解析出了关键词但库里没有对应商品 → 空结果」这种尴尬。模板回复同样只陈述状态里有的数据。而且降级是**可见的**：时间线写「规则解析 / 模板兜底」，商品区出现「规则兜底」徽标（仅干净的无 Key 路径）——不报错不等于生效，我要的是能看见。

### Q10 · SSE 为什么不用 WebSocket？事件模型怎么设计的？ `概率：中`

**一句话答案**
> 数据流本质是「客户端 POST 一次、服务端持续推」——单向就够。SSE 是普通 HTTP 响应，不需要额外的握手/心跳/连接管理，每个 API 路由保持无状态；用 `fetch` + `ReadableStream` 消费而不是 `EventSource`，因为要 POST 携带消息体、购物车快照、画像和待对比商品。事件模型是一份前后端共用的类型协议：10 种事件，前端按类型分发到时间线 / 商品区 / 面板 / 弹窗。

**展开讲法**
> 事件协议放在 `lib/agent/events.ts`，文件头写了一条硬约束：**只含类型与纯常量，禁止引入任何服务端模块**，否则会被打进客户端 bundle——「前后端解耦」在这里不是口号，是一个可检查的依赖方向。几个设计细节：① token 只推 `generateReply` 的（按 `event.metadata.langgraph_node` 过滤），否则 `parseIntent` 的结构化 JSON 会被当聊天气泡逐字打出来；② 快照里的 `reply` 按「本轮开始前的消息条数」界定本轮，否则中间快照会把上一轮的回复当成新回复推给前端；③ `toolCallLog` 在服务端按本轮起点裁剪再下发，因为日志时间戳也是服务端生成的，同一时钟比较才可靠；④ 图结束后**无条件**补推一次完整终态（原因见故事 D）。代价是客户端到服务端没有长连接：中断恢复是第二个 POST 端点（`/api/agent/resume` + `Command({ resume })`），不是在同一连接里回话。

**证据锚点**
- `docs/decisions.md` 第 10 条（含「需要双向时怎么办」「断线重连为什么不需要」）
- `lib/agent/events.ts:12-17`（禁止服务端模块）、`:82-92`（10 种事件）、`:44-80`（快照字段）
- `lib/agent/sse.ts:236-249`（token 过滤）、`:87-122`（`toSnapshot` 的 reply 与日志裁剪）、`:257-279`（终态补推）
- `lib/agent-client.ts:31,42`（中止单一入口与 AbortError 分类）

**如果被追问**
- *「不需要断线重连吗？」* → 这个场景不需要续传：状态由 checkpoint 承载，刷新后 `getState` 就是完整状态，前端重连等于重新发一次请求。
- *「为什么 `EventSource` 不行？」* → 它只支持 GET，带不了请求体；所以用 `fetch` 读流并按 `\n\n` 切帧。
- *「并发怎么办？」* → 同一 thread 硬串行化（`if (get().thinking) return`，UI 侧所有发送入口同时禁用），不同 sessionId 互不影响；理由是客户端无法终止服务端已开始的图执行，「打断重发」会让两个 run 同时写同一个 checkpoint（ADR 5）。

### Q11 · 数据源为什么不是实时爬取？为什么不做「一键更新」按钮？ `概率：中`

**一句话答案**
> 我实测过直连抓取：Amazon 返回 503（反爬拦截），淘宝/京东需要登录态 + 风控对抗，而且抓取违反平台协议、在国内还涉及《数据安全法》《反不正当竞争法》的合规风险。所以走的是「公开授权数据集 + 离线快照」这条合规路径：数据同样真实，而且不依赖运行时网络。一键更新按钮我不做，有三个具体理由，不是偷懒。

**展开讲法**
> 三条理由：① **按钮会暗示实时性**——我的卖点之一是「数据来源可追溯、快照冻结」，一个「更新」按钮会让人以为价格是实时拉的，而它其实是一次几分钟的构建任务；真实的东西用文字说清楚（来源、构建时间、重建命令），面板里就给这些，但它**只读、不执行**。② **长任务不该放进请求路径**——构建要下载数据集、跑归一化与去重，本地化首次还要几十批 LLM 调用（实测 420 件 ≈ 70 批 / 221.5 秒），塞进 Next.js 请求里会撞超时、无法中断、失败留半成品。③ **无鉴权的接口会烧配额**——这条链路一旦暴露成 HTTP 接口，任何人都能触发：justoneapi 源意味着真实计费调用（每件 1 次详情），本地化意味着烧自己的 token。更新只有一条路径：终端跑 `catalog:build && catalog:localize`（这两步是完整流程，不需要手工补救）。

**证据锚点**
- README「为什么不做实时爬取」段（503 实测）；`docs/api-sources.md`（逐源实测记录：URL、状态码、原样响应片段、限流头）
- README「为什么没有『一键更新』按钮」三条；`lib/catalog/field-truth.ts:74-79`（`REBUILD_COMMAND` 只给命令、不给按钮）
- README「更新数据只有一条路径」段 + 「跨产物继承」段（两步流程）
- 数字：全量本地化 70 批 / 221.5 秒

**如果被追问**
- *「数据集是哪来的？会不会也是爬的？」* → 是两个公开数据集（`luminati-io/eCommerce-dataset-samples`、`luminati-io/Amazon-popular-books-dataset`），Bright Data 官方发布的抓取样本；而我运行时用的第三方实时源是**付费 API**（JustOneAPI），不是爬取。
- *「那实时性怎么解决？」* → 用一个显式的可选源 + 图里一个条件触发节点：`enrichLiveData` 只在六条判定全满足时补 3 件商品的价格/库存，失败完全静默；它不是「让快照变实时」，而是「在需要时补一次真实值」。
- *「生产怎么办？」* → 生产应把数据更新改成定时任务，或直接替换为实时电商 API 客户端（`lib/catalog/products.ts` 是唯一入口）。

### Q12 · 目录扩容后为什么前 16 件逐字未变？「扩的是尾部」对谁成立、对谁不成立？ `概率：中`

**展开讲法**

### Q14 · 这个项目如果上生产，你会先补什么？ `概率：高`

**一句话答案**
> 按顺序补五件事：会话鉴权 + 按用户限流 + 单次请求 token 上限；checkpointer 换 PostgresSaver 并把 TTL 清理改成独立定时任务；数据更新从手动命令改成定时任务（或换成真实电商 API 客户端）；画像出境的合规评估与用户告知；最后补 UI 层的 E2E 回归。前两件是「不补就不能给别人用」，后面三件是「补了才敢放大流量」。

**展开讲法**

**证据锚点**
- §8 第 3 条（无鉴权/无限流）、第 12 条（画像出境）、第 10 条（快照需手动刷新）、第 4 条（checkpointer 已换 SQLite、剩余边界）

- `lib/agent/nodes/enrichLiveData.ts:35,38,65-92`（三层自保：3 件 / 60 秒 / 当日熔断）

**如果被追问**
- *「为什么不现在补？」* → 这个项目的定位是「可跑、可审、可演示的 Agent 架构样本」；加鉴权与限流需要账号体系，会把范围从「Agent 编排」扩到「用户系统」，收益与成本不成比例。我把边界写清并标在 §8 里，比假装做了更有价值。

## 3. 四个必讲的故事

> 格式：现象 → 定位过程 → 根因 → 怎么修 → 留下了什么防线。故事里的每个数字都能在 §1 找到出处。

### 故事 A · 图里的环差点撞上 `GraphRecursionError`

- **现象**：不是线上事故，是**设计期发现的风险**——「检索为空就放宽条件」这条路径如果一直不收敛，图会一直绕环直到 LangGraph 的默认递归上限抛错，而那个报错对用户毫无意义。（仓库里没有翻车记录，我不编一个。）
- **定位过程**：写图的时候先问「这个环什么时候停」。走到 `searchProducts` 之后有三个去向（继续细化 / 实时补充 / 生成回复），如果 `needsRefine` 由「结果为空」直接决定，而放宽条件是幂等的，那么「空 → 放宽 → 还是空」就没有出口。
- **根因**：图有环但没有**计数器**，收敛性没有被表达成状态。
- **怎么修**：状态里加 `refineCount`，条件边判定改成 `needsRefine && refineCount < MAX_REFINE_ROUNDS(=2)`；同时给放宽函数加单调性保证（`loosenFilters` 每次至少砍掉一个维度）；超限后不是死路，`generateReply` 给出可行动建议。
- **留下了什么防线**：① 常量只有一处定义（`state.ts:188`），条件边与节点都读它；② 时间线把「第 N/2 轮调整条件」写出来，放宽过程用户可见、也不会有第三轮；③ 相邻的一次真实修复（`8eee844`）补上了另一半：**主动细化**识别不出相对表述时不再无条件放宽（否则「换成第二件」会丢掉关键词、把范围从 8 件放到 16 件），并加了 `refineSearch.test.ts` 83 行单测。

**讲的时候可以补一句**：这条故事的价值不在「我修了一个 bug」，而在于「我给图里的环定义了退出条件，并把它写成了可断言的状态字段」。

### 故事 B · 落地校验拦下了模型自己编的金额——顺带暴露了一个显示缺陷

- **现象**：问「前两件加起来一共多少钱」，模型自己算出了 **¥2749** 并写进回复。数据里有单价、没有合计。
- **定位过程**：这个不是「偶然嘴瓢」——提示词里的「不要编造价格」是软约束，换一个更弱的模型就更容易出现；所以问题要定义成「回复进状态前有没有一道硬校验」，而不是「怎么把 prompt 写得更狠」。
- **根因**：LLM 输出被当成了可信输入直接渲染。同类问题还有两种变形：把评价数 84507 写成「销量 8.5万」（数字真实、标签错），以及自己把 84507 截断成「8.4万」（口径与界面不一致）。
- **怎么修**：① `grounding.ts` 抽全部 ¥ 金额逐个核对白名单（商品价 / 原价 / 数量小计 / 优惠 / 运费 / 应付 / 两两价差）；② 加「万」口径校验与「带标签数量」校验（销量只认真实销量集合、评价只认评价数集合）；③ 处理分两级：先点名「哪些数字不在数据里」让模型重试一次（用 `invoke` 非流式，避免两段候选拼进同一气泡），仍不符才降级模板；④ **顺带修的显示缺陷**：终态不是流式候选续写时，前端原先静默保留候选——用户看到的和 Agent 采用的是两段话，现在会整体替换气泡内容并停掉打字机。
- **留下了什么防线**：`parseIntent` 也把 LLM 失败原因写进时间线（不再静默吞异常）；校验与实时覆盖打通（覆盖值登记进白名单，否则回复引用实时价会被自己判成编造）；`demo-script.md` 第 7 步把这件事变成可现场演示的动作——「故意问一个数据里没有的数字，让面试官看到系统会拒绝回答」。

### 故事 C · 112 件已验收文案差点悄悄漂移

- **现象**：目录从 112 扩到 420 之后重跑完整流水线，比对发现**只有 16/112 件**的已验收文案逐字未变；`name` 66 处、`description` 92 处、`tags` 65 处、`specifications` 20 处被改写。当轮是靠一份不在仓库里的一次性脚本（`.cache/restore-approved.mjs`）逐字还原的。
- **定位过程**：先怀疑翻译质量，后来发现规律不对——被改写的都是「上一轮已经翻译过」的条目。于是查数据流：`catalog:build` 重新生成产物时会丢掉上一轮的本地化字段（中文 name/description/tags/specifications + `nameOriginal`），于是 localize 的「跳过已本地化条目」判据拿到的是全量英文条目 → **0 跳过 → 420 条全量重译（70 批 / 221.5 秒）**。
- **根因**：流程缺一步——「保住已验收文案」靠的是一次性脚本，而不是流水线本身。
- **怎么修**：① `catalog:build` 写盘前做**跨产物继承**：按「`id` 相同 **且** 旧产物 `nameOriginal`（英文原文）与新构建出的英文名**逐字一致**」双重校验，继承五个本地化字段，并打印「继承已本地化 N 条，待翻译 M 条」；② localize 的跳过判据与继承**共用同一份实现**（`isLocalizedProduct`：带 `nameOriginal` 标记即视为已本地化——这个字段只有 localize 写入，批次失败不会留半个标记）；③ 顺手修掉一个隐蔽误判：实测有 **40 件**（37 图书 + 2 Lazada + 1 Amazon）的译名与英文原文**逐字相同**（书名、品牌+型号，是模型的正确输出），用「中文名 ≠ 英文名」的判据会把这 40 件每次重建都重译一遍。
- **留下了什么防线**：纯函数单测 11 条（继承 8 条含「继承不修改价格/评分/评论数/销量/库存等非本地化字段」的键集合断言；A+ 降级 3 条）；构建与本地化两侧都打印同口径统计，让「为什么这次只翻了 N 条」在日志里自证；实测重跑 = 继承 420 条 / **0 批 / 0.38 秒**、`products` 数组深度相等、`git diff --stat` 只有两个时间戳。
- **可以主动补的延伸**：同一个判据还被 A+ CSS 那条修复用——2 件商品的源描述是亚马逊 A+ 页 CSS（5977 / 20747 字符），本地化后只剩「来自品牌」4 字；按裁定**降级而不是丢弃**（商品本身是好的），命中 CSS 特征就换成派生文案（与图书简介共用 `buildDerivedDescription`），产物打 `descriptionDerived` 标记。这个「描述基准变了 → 不继承 → 重译一次」的行为有单测锁着，所以它不会每轮都重译。

### 故事 D · 「模板回复不显示」——一个直接打穿卖点的 bug

- **现象**：一旦 LLM 不可用，回复气泡**完全不出现**（`reply` 恒为空）。这条直接打穿「没有 API Key 也能完整跑通」这个卖点。
- **定位过程**：`generateReply` 的 `node_end` 事件里读到的快照 `reply` 始终是空串。原因不是节点没写，而是**读的时机**：`node_end` 触发时节点刚结束，此时 `app.getState()` 读到的可能还是提交前状态（AIMessage 还没落进 state）。而 `reply` 是模板路径的**唯一**来源（该路径没有 token 事件，前端拿不到任何流式内容）。
- **根因**：快照推送依赖「节点结束事件」这个不保证状态已提交的时机。
- **怎么修**：图收尾时**无条件**补推一次完整终态（此时图已彻底结束，状态必然完整），前端 `applySnapshot` 对同一份状态幂等。
- **留下了什么防线**：这条修在 `b038ed3`，和「删除未接入的 `tool()` 契约」是同一个提交；README「跨层口径与流式输出」表里把它与另外五条同源问题放在一起（token 泄漏、气泡被拆碎、跨轮串联、总数不一致、被否决候选），共同根因是「同一个事实在不同层被各自解释了一遍」，修正方式都是把语义收敛到唯一实现。另外 `store/use-agent-store.ts` 那轮把打字机状态机重写成「用显式的本轮气泡 id」，气泡只在本轮真正结束时收尾——同源问题一次收干净。

**备选故事（如果面试官对「数据真实性」更感兴趣）**：库存件数是派生值却进过排序与推荐——界面显示「库存 231 件」、对比表实质按哈希排序、决策推荐把哈希值包装成「库存最充足 · 下单后发货更快」；修法是界面只展示等级、件数退回内部可用性模型、判优口径收敛到 `stockLevelOf()` / `STOCK_RANK`。**注意**：这条修复的代码变更在仓库初始提交里（`6b54d85`），**没有独立 commit 可引**，只能引 README「哪些是真实数据」段与 §8 第 2 条（见文末「证据最弱」）。

## 4. 能主动展开的深水区

面试官没问也可以引，每个点写「为什么这是个有含量的取舍」。

**① 失败隔离的边界：把「失败」定义成业务上的「没有」**
`enrichLiveData` 的契约是**永不抛错**——失败在业务上等价于「没有实时数据」，主流程照常走完。这不是「懒得分错误码」，而是一个明确的边界决定：节点不抛错，调用点就一个 `try/catch` 都不需要，主流程不可能被实时数据的可用性影响；错误信息不消失，而是变成时间线上一句中性的「实时数据不可用，已用快照数据」。同样的口径出现在客户端 chunk 加载（失败静默少几张卡、不显示「找不到」）与实时覆盖（部分失败只丢该件）。**有含量的地方在于「静默」是分场景的**：对用户静默，对评审不静默（时间线留痕）；而 `interrupt` 确认、下单这类**不可逆动作绝不静默**。
证据：`enrichLiveData.ts:236-245`（「不抛错是设计而非疏忽」）、`:263-270`（中性文案）、`client-products.ts:79-88`。

**② 事件协议怎么让前后端真正解耦**
`lib/agent/events.ts` 只放类型与纯常量，文件头明确禁止引入服务端模块——这条约束让「前端能拿到什么」变成可检查的依赖方向，而不是靠自觉；前端只认 10 种事件，服务端换 streamEvents 的版本、换节点、换 checkpointer，前端都不动。更难的一层是**谁裁剪、按谁的时钟裁剪**：`toolCallLog` 与 `reply` 都在服务端按「本轮起点」裁剪后再下发，因为时间戳也是服务端生成的，同一时钟比较才可靠；用客户端接收时刻过滤，会因为「图跑得比首字节到达还快」把所有条目丢掉。**有含量在于**：解耦不是「抽一个 interface」，而是把「哪个边界上产生的事实由谁裁剪」想清楚。
证据：`events.ts:12-17`、`sse.ts:73-86`（注释解释为什么服务端裁剪）、`:87-122`。

**③ 把「派生值不冒充真实值」从原则落到字段级**
这条原则被应用了两次，都是先把问题定义成「元信息撒谎」而不是「显示不好看」：销量（早期用「评价数 × 1.6」估算，会被卡片当销量展示、被 LLM 当事实引用）与库存件数（100% 派生却显示精确数字、决策推荐把哈希包装成理由）。修正方式不是改文案，而是**收敛唯一实现**：`hasRealSales()` 决定「有没有销量」，`stockLevelOf()` / `STOCK_RANK` 决定等级与判优，`lib/catalog/field-truth.ts` 决定字段分级——README、右栏「数据快照」面板、project-status 三处都引它。**有含量在于**：一个 UI 层的数字背后通常有三条链路（展示 / 上下文 / 对比判优），要三处同时收口才叫「不冒充」。
证据：`lib/utils.ts`（`hasRealSales`）、`lib/types.ts`（`stockLevelOf` / `STOCK_RANK`）、`lib/catalog/field-truth.ts:4-19`（为什么写进代码：三处手写必然漂移）、README「一条刻意遵守的原则」。

**④ 跨产物继承为什么必须双重校验（id + 英文原文一致）**
只按 `id` 继承看起来更省事，但数据源更新后可能「同一个 id 换了商品」或「标题被改」——那样旧中文文案会被安到别的商品上，而且是**无声的**（界面上看不出错，只有人肉比对才发现）。所以判据是：`id` 相同 **且** 旧产物 `nameOriginal` 与新构建出的英文名逐字一致；上游改了标题的条目会被重译一次，这是**刻意的**——标题变了，旧文案不再对应。配套还有描述基准 guard（A+ 降级那 2 件因为描述来源变了会重译一次，之后不再重译）。**有含量在于**：继承与跳过是同一份实现（`isLocalizedProduct`），两处各写一套口径必然漂移；「跳过」的判据用「标记存在」而不是「值相等」，是因为 40 件译名与原文逐字相同的正确输出会被等值判据误判。
证据：`scripts/catalog-shared.mjs:187-248`（`LOCALIZED_FIELDS` `:187`、`isLocalizedProduct` `:203-206`、`inheritLocalizedFields` `:223-249`）、`lib/catalog/catalog-shared.test.ts`（11 条）、README「跨产物继承」段。

**⑤ 内联卡：一个选取规则、两条路径、一个下发字段**
「这一轮回复该挂哪几张卡」曾只写在模板路径里（`searchResults.slice(0, 3)` 硬编码），LLM 路径没有——修的时候我没有在两个路径各写一遍，而是收敛成一个纯函数 `selectReplyProductIds`，由服务端快照字段 `replyProductIds` 下发给两条路径；「无商品不挂卡」是函数语义的一部分（闲聊 / 加购下单 / 对比轮 `searchResults` 为空）。**有含量在于**：真机验证时两条路径的卡片**数量一致（各 3 张）但列表不同**——因为两条路径的解析器不同（规则解析 vs LLM 解析），检索结果排序本来就不一样；「共用同一函数」靠单测锁定（同一份 `replyProductIds` 喂两条路径 → 同一 id 列表），不是靠两次真机的列表巧合。
证据：`sse.ts:54-71`（唯一实现）、`events.ts:66-73`、`store/use-agent-store.ts:129`、§7.1「内联卡修复」行（含这条「一处如实记录」）。

## 5. 边界与「我不知道」清单

> 原则：**主动划边界比被问出来强**。下面每一条都是「我能自己先说出来」的版本；括号里是出处。

### 5.1 安全与合规

- 「**没有鉴权、没有限流**——`/api/agent` 完全开放，配了 Key 就等于把 token 额度暴露给任何访问者。生产前必须加会话鉴权 + 按用户限流 + 单次请求 token 上限。」（§8 第 3 条）
- 「**用户画像会随 prompt 出境**到 LLM 服务商，demo 阶段没做任何合规处理：没有用户告知、没有数据处理协议、没有出境评估。画像本身不含敏感信息（地址、手机号、支付方式结构上就拿不到），但出境这件事我如实标在 README『隐私边界』里。」（§8 第 12 条）
- 「**画像没有 userId、不随账号迁移**，本质是同一浏览器下的记忆。」（§8 第 13 条）
- 「**时间线里的失败文本做过清洗**——服务商 401 文本会回显密钥末位，我加了 `sanitizeLlmError` 把它换成「服务商鉴权失败」并保留 401 与 request_id；口径与『token 不进日志/文档/commit』一致，右栏时间线同样是被截图、被讲述的界面。」（§8 第 21 条，commit `561e772`）

### 5.2 数据真实性

- 「**销量覆盖率只有 88/420**，其余 332 件显示『评价 X 条』。这是数据源决定的：只有 Amazon `bought_past_month` 与 Lazada `number_sold` 是真字段，Shopee 的 `sold` 全为 0、Walmart 根本没有这一列——这些一律记 0，不估算。」（§8 第 1 条）
- 「**75 件商品没有任何标签**（数码 13 / 服饰 2 / 食品 24 / 家居 6 / 运动 3 / 美妆 19 / 图书 8）：源数据没有 features、本地化文案里也不含功能词，派生不出来；带标签过滤的检索会排除它们。」（§8 第 9 条）
- 「**justoneapi 源缺评分 / 评论数 / 销量 / 划线价**——不是漏接，是京东搜索与详情端点里没有这些字段（实测为空串或『1万+』区间文案），一律记 0，界面按既有策略显示『暂无评分』。」（README「JustOneAPI 实时数据源」表）
- 「**京东库存状态码只实测到 33（有货）**；34/36/39/40 来自官方 IOP 文档枚举，没有逐一拿到缺货/预订的真实样本。」（§7.2）
- 「**2 件商品的描述是派生文案**（源描述是亚马逊 A+ 页 CSS，不可用），产物带 `descriptionDerived` 标记、字段分级表里如实标注。」（§8 第 22 条）
- 「**1456/1456 逐字比对的那次扩容验证，脚本不在仓库里**（`.cache/` 已 gitignore），只能引文档记录，不能现场复现。」（§7.1；这条我主动说）

### 5.3 架构与能力边界

- 「**实时覆盖只影响展示与回复，不重跑筛选 / 排序 / 推荐**：实时价大幅变化时它在『价格升序』里的位置不变。要改就得把覆盖值回注 `searchResults` 并重跑排序，那会破坏『哪个价格来自快照』的可追溯性——刻意不做。」（§8 第 17 条）
- 「**实时补充只在 `searchProducts` 之后触发**：意图被解析成 `compare` / `chat` 的问法（『那这几款现在多少钱？』『这几款还有货吗』）不经过检索节点，因此不会触发——这是图结构的直接结果，演示时要用 search / refine 类问法。」（§8 第 18 条）
- 「**客户端不再持有全量目录**带来三个边界：内联卡从『首帧就有』变成『chunk 到达后出现』（有同高占位，实测卡片 62px）；chunk 加载失败时内联卡静默缺失；某个 id 既不在渲染列表也不在会话缓存时弹窗不打开（正常交互到不了）。」同时如实说：「**『同高占位』只有构造性证据**，chunk 请求被拦截机制挡住，没能真机验证加载态。」（§8 第 24 条；§7.1 行 368）
- 「**`LLM_FALLBACK_ENABLED` 是死开关**：`isLlmEnabled()` 里那一支与随后的 `return isLlmConfigured()` 结果完全相同，两种取值行为一致。二选一（实现原语义 / 删掉变量）我还没做，README 已标『无实际效果』。」（§8 第 16 条；`lib/agent/llm.ts:26-29`）
- 「**页面刷新 / 导航不会中止在途请求**：浏览器卸载时会话与连接一起消失，服务端那一轮会跑完（无害但浪费 token），代码层没有可挽救的动作，只作为已知噪声记录（`net::ERR_ABORTED`）。」（§8 第 15 条、§7.3）
- 「**时间线不持久化、每轮重置**：它是当轮推理的视图，刷新后看不到上一轮条目——这是设计，不是 bug。」（`demo-script.md` 准备事项；`store/use-agent-store.ts`）

### 5.4 验证缺口（能主动说出来的「没有证据」）

- 「**没有组件测试与 E2E**：单测覆盖 `lib` 纯函数与 store 不变量（381 条），界面回归靠手工浏览器验收 + 证据入库（截图、几何实测）。代价我认：界面重构没有自动化护网。」（§7.2）
- 「**暗色模式没有截图**，只有同源 iframe 里的测量式证据（令牌命中 `.dark`、对比度全部 ≥ WCAG-AA、画布像素可读）。」（§7.2）
- 「**以图搜商品没实测**——需要支持视觉的模型；代码路径（多模态消息组装）是有的。」（§7.2）
- 「**极端时序没压测**：气泡计数一致性只验了 3 轮，没有长会话与并发压测。」（§7.2）
- 「**`justoneapi` 源下没走完加购 / 对比 / 下单**：只补验了『检索 → 实时补充 → 回复』这条主链路。」（§7.2、`demo-rehearsal.md` 第九节）

### 5.5 刻意不做（防线式表述，别用「还没做」）

- 不做语义记忆 / RAG（ADR 3）；不做 tool calling（ADR 2）；不做「打断重发」——客户端无法终止服务端已开始的图执行，拒绝第二条消息是最小且正确的选择（ADR 5）

## 6. 压力问题（要有话术，不是硬扛）

> 原则：**承认事实 + 说清判断 + 给可验证的替代证据**。不要辩护。

**Q：这个项目 AI 参与了多少？哪些是你自己判断的？**
> 诚实版本（比例按你的真实情况替换）：**代码实现大量是 AI 辅助产出的，但架构取舍、验收标准和红线是我定的**。我建议这样举证，而不是空口说比例：① 这个仓库里每条 ADR 都写了「代价」段——那是取舍思考的痕迹，AI 不会主动去写「我失去了什么」；② §8 的 25 条已知问题里，有「已修」「决定不改」「边界」三种标注，其中「决定不改」的三条（如意图面板字段名）都写了不改的理由——这是我按「超出授权就停下」的规则裁定的；③ 每一轮任务的验收标准（比如「锚定 `.env.local` 只读」「JustOneAPI 配额 0 次计费」「跑 build 前先停 dev」）都是我先立规矩，再让实现去满足；④ 失败路径必须取证（无效 token 的浏览器截图）、内部 LLM 错误文本必须清洗——这些纪律不是 AI 的默认行为，是我加的。可以补一句：**AI 写代码这件事我不掩饰，我更想被检验的是『你怎么验收』**。

**Q：为什么没有 E2E / 组件测试？**
> 事实：单测 363 条全部在 `lib` 纯函数与 store 不变量这一层，界面回归靠手工验收。这是我**有意选的成本结构**：纯函数层是我改动最频繁、回归代价最高的地方（解析器、判定、金额、继承逻辑），而 UI 是展示层。代价我不回避——界面重构没有自动化护网，所以每轮验收都留证据（截图、几何测量、「失败/错误/重试 全 0」这类文本断言）。如果补，我会按这个顺序：一条主链路 E2E（搜索 → 对比 → 加购 → 结算 interrupt → 恢复），然后是两个组件测试（内联卡的延迟渲染与静默失败、store 的硬串行化）——它们是目前「手工验过、代码里没有不变量」的两处。

**Q：为什么不上生产？**
> 因为有三件事没做，而它们是**前置条件**而不是优化项：① 无鉴权、无限流——配了 Key 就等于把 token 额度公开；② 会话持久化是 SQLite 单文件 + 同步 API，清理闸门依赖进程内变量，生产要换 Postgres + 定时任务；③ 快照需要定时重建，或换成真实电商 API 客户端。外加一条合规：画像会随 prompt 出境且没有告知与评估。我把这些逐条写在 §8 和 README 里，而不是含糊说「demo 阶段」。这个项目的目的不是上线，是**把 Agent 编排的取舍讲清楚并让它可被审查**——上生产是另一个量级的系统（账号、权限、计费、风控），我不假装它已经有了。

**Q：一个人做的？**
> （按你的真实情况回答。）关键不是人数，而是**怎么在没人 review 的情况下不骗自己**。我的做法：每个结论都留出处并区分三态（实测 / 推断 / 未验证）——这份仓库里连「降幅 127 kB」都要写清是探针实测还是文档记录；失败路径必须取证，不能只测成功路径；验收标准事先写死（比如「配额 0 次计费」），事后再报数。正因为是一个人，我才把「可复现」当成纪律：构建产物、单测、截图、几何实测都在仓库或文档里能指到。

**Q：数据是爬的吗？合法吗？**
> 不是爬的——运行时完全不抓取。目录来自两个 **Bright Data 官方发布的公开数据集**（`luminati-io/eCommerce-dataset-samples`、`luminati-io/Amazon-popular-books-dataset`），本质是抓取**样本**的再发布，我在构建脚本里只做归一化、去重、汇率折算与本地化。我**实测过直连抓取并放弃**：Amazon 返回 503（反爬），淘宝/京东要登录态与风控对抗，抓取违反平台协议、在国内还涉及《数据安全法》《反不正当竞争法》的合规风险——这是我选「公开授权数据集 + 离线快照」的直接原因，记录在 README 和 `docs/api-sources.md` 里。运行时的第三方数据源（JustOneAPI）是付费 API，不是爬虫。

**Q：目录才 420 件，这也叫电商系统？**
> 规模上我承认它小。但我想请你换个角度看：**这是一份「数据真实性可被逐条追问」的目录**——420 件里只有 88 件有真实销量，我就标 88；只有 279 件有真实划线价，我就标 279；库存件数是派生的，我就把界面改成只显示等级；2 件商品的描述源是 A+ 页 CSS，我就降级成派生文案并打标记。**很多规模大得多的系统做不到把每一条数据的来路说清楚。**另外规模不是架构天花板：`lib/catalog/products.ts` 是唯一入口，接真实电商 API 或加检索层时，节点与组件都不动——我在 ADR 里写的就是「商品涨到 10 万件需要的是检索层，不是把偏好向量化」。

**Q（可能的变体）：这些都是你自己写的吗？/ 你有什么没搞懂的地方？**
> 直接给一个「我不确定」清单比硬撑更可信，比如：京东库存状态码我只实测到 `33`，其他来自文档枚举；构建期更大规模（`--per=14`）的配额上限与耗时没实测；断网场景是按代码路径推断的，没做真实演练。这些在仓库里都有标注——我宁可你看到我不知道的边界，也不想给你一个「全都搞定了」的印象。
