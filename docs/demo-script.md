Beneath a Scarlet Sky（Mark Sullivan）¥94，原价¥201，4.7分，评价5.6万 …」——**首句措辞与具体书单每次会变**，但「12 件 / 列前 5 件」是稳定的）<br/>中栏：标题变为「搜索结果 · **共 30 件 · 展示前 12 件** · 图书 · 小说」（2026-09-26 起中栏写明展示口径：命中数 > 展示数时同时给出两个数字），网格刷新为 12 本书<br/>右栏：时间线 3 条 —— `识别意图：搜索商品｜LLM 解析（JSON 模式） · 历史 N 字 · 图书 · 小说`、`检索「图书 · 小说」｜命中 30 件，展示前 12 件`、`生成回复｜LLM 生成`；意图解析面板显示品类「图书」、关键词「小说」<br/>**已有画像时**，第 1 与第 2 条之间会多一条 `记起你的偏好：图书｜本轮输入未给出品类/关键词，参考了历史偏好（来源：…）` |

| --- | --- |

| **预期画面** | 右栏「对比分析」面板出现 3 列对比表：**固定行**（价格 / 原价 / 评分 / 库存 / 性价比 / 类目）+ **随所选商品而变的参数差异行**（实测为 作者 / 装帧 / 重量 / 尺寸；图书没有「品牌」行），差异项高亮、各维度最优标绿底，表下注明「标记为存在差异；绿色底为该维度最优」；时间线 `对比 3 件商品｜共 10 项参数，其中 9 项存在差异 · 性价比最高：Beneath a Scarlet Sky：小说（¥94）`（2026-09-25 扩容后实测；**被对比的 3 件随当轮检索结果而定**）；「决策推荐」面板给出量化理由<br/>⚠️ 中栏商品卡**不会**出现多选标记 —— 卡片上的勾选是**你自己**点「加入对比」时的选中态，Agent 的对比不会点亮卡片 |

### 第 4 步 · 加购（约 20s）

| | |
| --- | --- |
| **操作** | 输入「把第一件加入购物车」 |
| **预期画面** | 左栏：加购结果（含商品名与金额）<br/>右栏「购物车」面板出现该商品 + 数量控件 + 金额明细（顶栏购物车图标打开的抽屉里是同一份内容）。明细行是 `商品合计 / 商品直降 / 运费 / 应付`（「优惠券」行**只在满 300 减 30 生效时**出现）——示例：单件 ¥94 时为 `商品合计（1 件）¥94 / 商品直降 −¥107 / 运费 包邮 / 应付 ¥94`（**具体商品与金额随当轮检索结果而定**，2026-09-25 扩容后第一件是 Beneath a Scarlet Sky）；标题上的件数角标 +1<br/>时间线：`识别意图：购物车操作 … 定位到第 1 件：…`、`加入购物车｜…｜已将 … × 1 加入购物车` |
| **证明什么** | 购物车是**双端一致**的：服务端图状态是唯一事实来源，面板上的增减会作为快照回传，因此「界面上看到的金额」与「下单时的金额」不可能分叉。 |

### 第 5 步 · 下单（human-in-the-loop，约 40s）

| | |
| --- | --- |
| **操作** | 输入「结算」→ 弹出订单确认弹窗 → 点「确认下单 · ¥XXX」（金额 = 购物车实付；示例：单件 ¥94 时为 `确认下单 · ¥94`） |
| **预期画面** | 弹窗展示订单明细（商品行、收货地址、支付宝、`商品原价合计 / 商品现价合计 / 运费 / 应付`——数字随购物车变化，示例仅示意）；确认后弹窗收起、购物车清空（面板回到空状态、角标消失）<br/>右栏时间线：`订单已确认：ES…｜1 种商品，实付 ¥XXX`、`下单成功：ES…｜1 种商品，实付 ¥XXX，已清空购物车`（当轮还会有第 3 条 `生成回复`；订单号由 `thread_id + messages.length + 购物车` 派生，每次不同）<br/>界面上可核对的就三件：弹窗收起 + 购物车清空 + 上面两条时间线（页面**没有**单独的「订单状态」字段，状态在服务端图里） |
| **证明什么** | `interrupt` 暂停 + `Command(resume)` 恢复的完整闭环：**下单前必须人工确认**，且订单号由 `thread_id + messages.length + 购物车` 派生 —— 节点重入两次也只有一个单号（同一会话连下两单不会撞号）。 |

> 注：确认后的**回复气泡文案由模型自由生成、偶尔会偏题**（实测有一次在复述检索结果）；以弹窗、时间线与购物车状态为准，这一点在无 Key 路径下反而更干净（模板回复会明确报出订单号）。
> 另：当轮的 `生成回复` **可能带落地校验重试文案**（如 `落地校验未通过（疑似编造金额 ¥200），已按纠正提示重试一次并采用重试结果`）——2026-09-25 彩排第 5 步就触发了一次。这不是异常，是第 7 步那道防线的常态，任何一步都可能出现。
> **回归防线（2026-09-26 起）**：确认下单后，**再发任何消息都不会再弹出结算弹窗**（本轮修掉了「已结账仍复发」的缺陷）。若现场再次弹窗即为回归，不要继续演，直接切到 [demo-rehearsal.md](./demo-rehearsal.md) 的 Plan B。小坑：模型偶尔会把**已确认**的订单称作「待确认」（有一轮回复写了「另有待确认订单 ES…」）——状态看时间线与订单历史（`已确认 · 待发货`），不要照念回复。

| --- | --- |
| **操作** | 点对话区标题栏的「开启新会话」（消息清空、thread 轮换）→ 输入「推荐点什么」 |

### 第 7 步 · 落地校验（约 40s）

| | |
| --- | --- |
| **操作** | 输入「前两件加起来多少钱」 |
| **预期画面** | 左栏回复：「前两件是 **Where the Crawdads Sing** ¥180 和 **The Boy, the Mole, the Fox and the Horse** ¥75。两件价格数据里都有，但合计金额数据里没有，我不能自己算。」（措辞与被引用的两件都随当轮结果变化，**要点是拒绝自行求和、只原样引用单价**）<br/>右栏时间线：`识别意图：…｜…ms`（**意图标签随问法波动**：实测出现过「闲聊兜底」「商品对比」，不要现场承诺固定标签）、`生成回复｜2115ms｜LLM 生成 · 落地校验未通过（疑似编造金额 ¥XXX），已按纠正提示重试一次并采用重试结果`（被拦金额随当轮上下文变化，实测出现过 ¥255 / ¥1246） |

### 第 8 步 · 无 Key 降级（约 30s，需重启）

| | |
| --- | --- |
| **操作** | 把 `.env.local` 的 `LLM_API_KEY` **清空** → 重启 `npm run dev` → 输入「推荐几本小说」（或「推荐几本耳机」） |
| **预期画面** | 中栏仍出商品（12 件小说）；右栏时间线 `识别意图：搜索商品｜规则解析 · 小说`、`生成回复｜模板兜底`（**全轮不再出现「LLM 解析 / LLM 生成」**）；模板回复以「为你找到 12 件符合条件的商品（图书 · 小说）：…」开头；若画像有信号，末尾会带出「注意到你之前买过图书，需要我按这个方向再找找吗？」；商品区标题旁出现 **`规则兜底` 徽标**<br/>⚠️ **前提**：徽标只在 `llmEnabled=false`（Key 为空 / 缺失）时渲染。若**不能改 `.env.local`**（例如只读环境），可改用 `$env:LLM_API_KEY='invalid-demo'; npm run dev` 注入**无效但非空**的 Key：降级照常发生，但 `llmEnabled` 仍为 true、**没有徽标** —— 此时取证看时间线（`规则解析 · LLM 失败：401 …`）。两条路径都已在 2026-09-25 / 2026-09-26 实测（见 [demo-rehearsal.md](./demo-rehearsal.md) 第四节与第十节）<br/>⚠️ 规则路径的条件串可能只有题材词（实测为 `检索「小说」`，不带品类），与 LLM 路径的 `图书 · 小说` 不同 |
| **证明什么** | 全链路可降级：规则解析器（词表全部从商品目录派生）+ 模板回复（数据 100% 来自状态）让**没有 API Key 也能完整跑通**，而且降级是**可见**的（时间线与徽标都会说明当前走的是哪条路）。 |
| **彩排实测（2026-09-25）** | 本步不止能搜索：**对比 → 加购 → 结算 interrupt → 确认下单** 在无 Key 下全部走通（订单号 `ES20260925995029`、实付 ¥180、购物车清空），时间线每步 1ms 级；本步的主要时间成本是**重启 dev**（约 20–30s），不是对话 |

> 注意：`LLM_FALLBACK_ENABLED=false` **不足以**演示规则路径 —— 只要 Key 仍在，`isLlmEnabled()` 仍为真。要演「干净的规则路径」（带徽标）必须**清空** Key 后重启。
> 若只写一个**无效值**（Key 仍在），系统同样会降级（时间线写 `规则解析 · LLM 失败：…`），但 `llmEnabled` 仍为 true、**商品区不会出现「规则兜底」徽标** —— 那种情况请指向时间线（详见 [demo-rehearsal.md](./demo-rehearsal.md) Plan B1）。
> 两个无 Key 下的展示差异（彩排实测，不影响结果）：① 意图面板把题材词显示为「**功能** 小说」（LLM 路径是「关键词 小说」）；② 同一 thread 若先跑过 LLM 路径再切到无 Key，条件串可能重复一个词（如 `图书 · 小说 · 小说`）——跨解析来源合并所致，检索结果不受影响。

| **配额与耗时** | 首次演示约 **3 次计费**（每件 1 次价格调用；问到货再 +1 次/件）。**这一步明显比别的步骤慢**：实测第 ② 轮约 17.5 秒（节点 16.0 秒 = 三次调用 2.7 / 3.4 / 9.9s + 生成回复 1.4s）——等待时说明「正在查京东实时接口」即可，不要以为卡死。同一商品 5 分钟内命中进程内缓存、不再计费；同一 thread 60 秒内不会重复触发（追问太快会没反应，属预期） |
| **诚实说明** | **价格可能一点没变** —— 那正是真实结果（快照构建时刻与现在相隔不久）。这一步证明的是「图里有条件触发的实时补充、且不影响主流程」，不是「价格一定变了」。若想看到数值变化，用 `real` 源做对照：同样的问法下不会出现任何「实时」标注 |
| **证明什么** | ① 条件触发（六条判定）写在**边**里、可逐条单测；② 覆盖只作用于展示与回复上下文（不改筛选/排序/推荐），且 `liveOverrides` 与 `searchResults` 分开存，所以「哪个价格来自实时」是可追溯的；③ 失败完全静默——把 token 改成无效值再跑一遍，对话照常、只在时间线留一条「实时数据不可用，已用快照数据」（**补充轮已做浏览器取证**：无标注、无报错弹窗、无「重试/确定」交互，见 [demo-rehearsal.md](./demo-rehearsal.md) 第三节末尾） |
| **追问应对** | *为什么只补 3 件？* → 单轮配额上限（每件 1 次调用，问到货 +1 次）。*为什么没有评分？* → 京东搜索与详情端点里没有评分字段（实测为空串/区间文案），拿不到的东西不假装有（见 README「JustOneAPI 实时数据源」）。 |

## 两分钟精简版

时间紧就只讲「编排 + 真实性 + 记忆」三件事，四步：

| 步 | 操作 | 一句话证明 |
| --- | --- | --- |
| 1 | 「推荐几本小说」 | 自然语言 → 意图与条件在右栏可审计（时间线 3 条 + 意图面板） |
| 2 | 「刚才那个再便宜点」 | 短期记忆参与理解：只放宽一轮，条件 `图书 · 小说 → 图书 · 小说 · ¥200 以内` 写在时间线上 |
| 3 | 「开启新会话」→「推荐点什么」 | 跨会话记忆：新 thread 里自动落到图书，时间线出现「记起你的偏好：图书（来源：成交）」 |
| 4 | 「前两件加起来多少钱」 | 落地校验：拦下编造的 ¥255 → 纠正提示重试 → 只引用单价 |

四步覆盖了**编排可审计 / 记忆可解释 / 数据不可编造**三条主线，且都在右栏同一条时间线上连续可见 —— 不需要切换页面。彩排实测：这四步的系统侧耗时合计约 **11.5 秒**（讲解时间另计）。

> 现场翻车时的说法（模型服务不可用 / 实时配额用尽 / 断网）见 [demo-rehearsal.md](./demo-rehearsal.md) 的「演示翻车预案」，都是可以照念的具体操作。

## 演示时的四个加分动作

1. **指时间线而不是回复**：每一步都说「看右栏这条」，把「模型说的话」与「系统做的事」分开 —— 这是本项目与「套壳聊天」最大的区别。
2. **故意问一个数据里没有的数字**（第 7 步），让面试官看到系统会**拒绝**回答而不是编一个。
3. **点一下「你的偏好」面板的「清除画像」**，说明清除后 `generation` 自增、在途请求带回来的旧信号会被丢弃（清除是有效的，不会被并发覆盖）。
4. **演一次「搜索无结果」**（约 15s，可选）：在**新会话**里输入「十万元以上的商品」→ 中栏标题变为 `没有找到符合条件的商品`、副标题 `试试放宽条件（价格 / 品类），或看看下面的推荐`，下方仍给 12 件精选（带「为你推荐」小标题），**不会显示「0 件商品」、也不是空白页**。⚠️ 演示完请点一次「开启新会话」：这类问法会把 `minPrice` 留在检索条件里（浅合并语义，见 [demo-rehearsal.md](./demo-rehearsal.md) 第十节 F1 与 project-status §8 第 32 条），不清理的话后续搜索会一直带着这个下限。
