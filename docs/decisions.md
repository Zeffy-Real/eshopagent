# 技术决策记录（ADR）

> 来源：README、`docs/project-status.md`、代码注释里的既有结论**汇总**，不是事后重新发明。
> 每条格式统一：**背景 / 选项 / 决策 / 理由 / 代价**，末尾附 **如果被追问**（面试官最可能接着问什么、怎么答）。

## 1. 为什么用 StateGraph 而不是 AgentExecutor

- **背景**：Agent 需要 6 类意图分流、一次受控的「检索 ⇄ 细化」循环、以及下单前的人工确认，同时要把过程实时画出来。
- **选项**：`AgentExecutor`（黑盒循环，靠 Prompt 引导模型选择动作）／自己写 while 循环 + 状态机／LangGraph `StateGraph`（显式状态 + 声明式条件边）。
- **决策**：StateGraph。
- **理由**：AgentExecutor 的中间过程不可控、不可视化，也无法表达「循环两轮就强制收敛」这种约束；自研状态机要自己处理状态合并、并发写入、checkpoint 与中断恢复。StateGraph 的 reducer 机制天然解决状态合并（`messages` 追加、`searchFilters` 浅合并），`streamEvents` 直接产出 `node_start` / `node_end` 结构化事件 —— 恰好是右栏时间线需要的形状。
- **代价**：要自己定义全部状态字段与 reducer，比「写个 Prompt 就完事」多一层样板；节点必须遵守「状态写入只发生在节点内」的约束。
- **如果被追问**：*循环会不会失控？* → 环只有一个（`refineSearch ⇄ searchProducts`），由 `refineCount < MAX_REFINE_ROUNDS(=2)` 封顶；再问「为什么是 2」→ 实测「去标签 → 去关键词 → 放价格 → 去品类」四条放宽路径，两轮足以覆盖大多数空结果场景，再多轮用户已经看不到「为什么放宽了」。

## 2. 为什么不用 tool calling（评估后刻意不采用）

- **背景**：项目有 8 个预定义节点、6 类有限路由，工具与节点几乎一一对应。
- **选项**：`bindTools` 让 LLM 在运行时挑工具（当时甚至已经写好了 `tool()` 契约）／节点直接调用纯函数。
- **决策**：不接入 tool calling，删除已写好但从未被引用的 `tool()` 包装。
- **理由**：tool calling 解决的是「运行时动态选择**未知**工具集」—— 这个问题在本项目里**不存在**。接进来不解决任何实际问题，只是在 StateGraph 之上再叠一层隐式 agent 循环（图已经定义了流程，工具选择却被交给模型）＝架床叠屋。StateGraph 的哲学是「图本身就是编排层」，节点直调纯函数是它的自然延伸。**「评估过并判定为多余间接层」比「为了用而用」更有说服力**。
- **代价**：失去「模型自主组合工具」的能力 —— 但本项目不需要；新增能力要显式加节点 + 连边（这被认为是优点：路由可预测、可测试）。
- **如果被追问**：*那 LLM 参与什么决策？* → 两处且都是结构化输出：`parseIntent` 决定意图与筛选条件（条件边的依据），`manageCart` 解析购物车指令。*想加 tool calling 呢？* → 只有当工具集不确定、需要模型自主编排多步任务时才值得，那时图的形状也会跟着变成 ReAct 式循环。

## 3. 为什么不做语义记忆 / RAG（记忆第四层）

- **背景**：目录是 112 件**结构化**商品（品类 / 品牌 / 价格 / 评分 / 参数 / 标签齐全），偏好用「品类 + 品牌 + 关键词 + 价位」四字段已能覆盖检索与推荐。
- **选项**：向量库 + embedding 做语义记忆／继续用结构化字段。
- **决策**：不做（明确写进 README「记忆机制」）。
- **理由**：三条，都是「在这个项目里不成立」而非「RAG 不好」——① 这么小的结构化数据集，向量检索不会优于「关键词 + 标签过滤 + 排序」，只多一层近似匹配的不确定性；② embedding 要么再依赖外部 API（多一个 Key、多一份数据出境面）要么引入本地模型，会破坏「没有 API Key 也能完整跑通」这条基线；③ 同时讲 LangGraph 与 RAG 两套架构会稀释表达重点。
- **代价**：无法处理「语义相近但字面不同」的模糊偏好（例如「想要送礼体面的」）；当前靠同义词映射（`跑鞋 → 跑步鞋 / 运动鞋`）与标签派生部分覆盖。
- **如果被追问**：*商品涨到 10 万件呢？* → 那时需要的是**检索层**（倒排索引 / 向量召回）而不是「把偏好向量化」；`catalog/products.ts` 是唯一入口，替换成真实电商 API 或带检索的服务即可，上层节点与组件不动（README「可扩展性」已写明）。

## 4. 为什么 checkpointer 设计成可替换（Memory → Sqlite 零改动）

- **背景**：初版是 `MemorySaver`，进程重启丢全部会话；生产环境需要落盘。
- **选项**：业务代码直连数据库／把持久化收敛到 checkpointer 一处。
- **决策**：只改 `lib/agent/checkpointer.ts` 一个文件，对外只暴露 `getCheckpointer()` 与 `threadConfig(sessionId)`；`CHECKPOINT_BACKEND=memory|sqlite` 可切，初始化失败自动回落内存态。
- **理由**：LangGraph 的 checkpointer 就是持久化抽象点，8 个节点只依赖那两个函数（全仓库没有任何地方 `new MemorySaver()`）。换后端时业务代码零改动 —— 唯一例外是 `graph.ts` 的类型签名从 `MemorySaver` 放宽为 `BaseCheckpointSaver`。SqliteSaver 用 `new Database(path)` 自行开连接，是为了能设 `WAL` + `busy_timeout=5000`（dev 热更新残留连接会撞锁）。
- **代价**：`better-sqlite3` 是原生模块（安装可能失败 → 已用动态 import + 自动回落兜住）；同步 API 会阻塞事件循环（单机 demo 可接受）；SQLite 文件含完整对话内容，必须保持 gitignore。
- **如果被追问**：*生产怎么换？* → `PostgresSaver` 替换同文件；惰性 TTL 清理改成独立定时任务（当前「新会话创建时 + 10 分钟最小间隔」的闸门依赖进程内变量，dev 热更新会重置它，只是多扫一次表，无正确性问题）。

## 5. 为什么硬串行化（`thinking` 门闸）而不是允许并发

- **背景**：同一 `thread_id` 上并发跑两个图，checkpoint 会互相覆盖（后写入的整份状态盖掉前一份），表现为对话内容错乱。
- **选项**：允许并发 + 加锁／队列化前一条／硬串行化：前一转未结束就拒绝新的发送。
- **决策**：硬串行化（`if (get().thinking) return`），并在 UI 侧把所有发送入口一并禁用（发送按钮 / 品类 chip / 购物车与对比按钮 `disabled`，顶栏搜索框 `handleSubmit` 提前 return）。
- **理由**：客户端无法终止**服务端**已经开始的图执行（Node 不会因为连接断开就停止），所以「打断重发」会让两个 run 同时写同一个 checkpoint —— 正是串行化要防的事。拒绝第二条消息是最小且正确的选择：不说话，也不写坏状态。这条不变量用单测锁死（`store/use-agent-store.test.ts`：`fetch` 只调用一次、第二条不进入消息列表）。
- **代价**：用户不能在等回复时补一句话，必须等本轮结束；长回复期间体感被锁。
- **如果被追问**：*为什么不做「打断重发」？* → 需要先在服务端实现取消（把 `request.signal` 透传到图执行、必要时回滚到上一个 checkpoint），属于另一个量级的改动，当前明确不做。*并发用户呢？* → 不同 `sessionId` 互不影响，串行化只作用在单个 thread 内。

## 6. 为什么记忆分四层、第三层极简、第四层不做

- **背景**：把「记忆」当成一个功能做，会得到一堆互相冲突的字段与策略。
- **选项**：一次性设计完整的记忆体系／按**作用范围**分层，各层用最合适的介质。
- **决策**：四层 —— ① 会话内短期记忆（历史注入，`lib/agent/history.ts`）；② 会话持久化（checkpointer，按 `thread_id`）；③ 跨会话结构化画像（localStorage，4 个字段）；④ 语义记忆（不做）。
- **理由**：前三层的作用范围不同（当前这个 < 同一个 thread < 同一浏览器），介质也就不同：prompt 上下文 / 图状态落盘 / 浏览器本地。第三层故意**只有 4 个字段**（最近搜索、品类偏好、品牌偏好、价位带），因为字段越多越难解释每一项的来源 ——「画像每一项都能追溯到一次真实操作」是可追溯性的硬要求，而第四层的取舍见第 3 条。
- **代价**：第 1 层超出字符预算就整轮丢弃（更早的指代对象不在上下文里）；第 3 层换了浏览器就丢（见第 7 条）。
- **如果被追问**：*四层会不会互相污染？* → 会，且已经处理：历史只用于**消解指代**不用于推断意图类别；画像只影响**回复措辞**不参与筛选条件（规则路径）；画像信号只从真实行为提取、没有行为就没有字段。

## 7. 为什么画像存 localStorage 而不是服务端

- **背景**：跨会话画像需要一个存储位置，而项目没有账号体系。
- **选项**：服务端表 / 按 `sessionId` 存 / localStorage。
- **决策**：localStorage，且与 `sessionId` **解耦**（按 sessionId 存会让「新会话」读不到画像，直接违背验收标准）。
- **理由**：① 没有 userId，服务端存了也无法归属；② 存 localStorage 就天然解耦，前端每轮把画像作为**一次性上下文**上行（走 `config.configurable`），服务端用完即弃 —— 服务端不持有画像，也不写进 checkpoint；③ 用户能自己清（右栏一键清空，`generation` 自增让在途信号失效）。
- **代价**：本质是「**同一浏览器下**的跨会话记忆」，不是跨设备 / 跨用户；清浏览器数据即丢；而且画像摘要会随 prompt 出境到 LLM 服务商（demo 阶段未做合规处理，README 已如实标注）。
- **如果被追问**：*换设备怎么办？* → 要引入账号体系 + 服务端存储 + 数据出境评估，是另一个量级的改动；当前把边界写清楚，而不是假装支持。*为什么不用 IndexedDB？* → 画像只有 4 个字段、几 KB，localStorage 的同步读写更简单，也不需要处理版本迁移。

## 8. 为什么纯函数 + zod 校验而不是 `tool()` 包装

- **背景**：工具层需要被节点调用，同时需要入参校验。
- **选项**：`tool()`（name/description/schema 三元组，供 LLM 绑定）／纯函数 + 就地 zod schema。
- **决策**：纯函数 + zod schema，节点直接调用；schema **不集中**到一个 `schemas.ts`。
- **理由**：`tool()` 的价值在于把工具暴露给模型（见第 2 条，本项目不需要）。保留的 schema 承担**三处不同层**的运行时校验：LLM 输出契约（`IntentSchema` / `CartActionSchema`）、节点入参、HTTP 请求体（`cartLineSchema` 被 `/api/agent` 复用，消除了原先手写的重复约束）。因此 schema 与它校验的对象放在一起——集中放一份反而会让「谁在约束谁」变模糊。
- **代价**：没有统一的工具清单可以展示（README「工具层」表格充当这个角色）；新增工具时要手动在节点里 import。
- **如果被追问**：*LLM 输出的校验够严吗？* → `IntentSchema` 除 `intent` 外全部 nullish（模型漏填不会整次失败，只是该维度不参与筛选），并且金额与口径还要过 `grounding.ts` 的落地校验 —— 结构化校验只管形状，落地校验管事实。

## 9. 为什么库存只显示「有货 / 紧张 / 缺货」而不显示件数

- **背景**：真实数据源里**没有任何一件商品带真实库存件数**（只有 Shopee 有 `stock` 字段，而当前目录已无 Shopee 商品），目录里的件数全部是构建期 `21 + hash % 480` 派生的。
- **选项**：把派生件数当真实数据展示／不展示件数、只用等级。
- **决策**：界面一律只展示等级；件数退回**内部可用性模型**（缺货不可加购、加购数量上限、性价比的缺货惩罚）。
- **理由**：早期版本在详情弹窗、对比表、决策推荐里展示「库存 231 件」，还输出过「库存最充足（231 件）· 下单后发货更快」—— 那是在**把哈希值包装成推荐理由**，与「数据真实」这条卖点直接冲突（对比表的「库存」行实质是按哈希排序）。修正后：对比表按**等级**判优，「现货可发」这条推荐只在等级确实有差异时才产出（全部有货时它不区分任何商品）。判优口径收敛到 `lib/types.ts` 的 `stockLevelOf()` / `STOCK_RANK`。
- **代价**：用户看不到具体可购数量（加购超量时只能得到「库存不足，请减少数量」这类提示，不含数字）。
- **如果被追问**：*那件数还要它做什么？* → 三个功能判断（是否缺货 / 加购上限 / 缺货惩罚）；*换成真实库存数据呢？* → 恢复展示件数是改一处 `stockLevelOf` 调用点的事，但要有真数据源 —— 与「没有数据就显示没有」这条原则一致。

## 10. 为什么用 SSE 而不是 WebSocket

- **背景**：Agent 执行过程要实时呈现（节点事件、token 流、状态快照、中断），客户端还要把消息体、购物车快照、画像、待对比商品传上去。
- **选项**：WebSocket（双向）／轮询／SSE（服务端单向推送）。
- **决策**：SSE，用 `fetch` + `ReadableStream` 消费（**不是** `EventSource`）。
- **理由**：数据流本质是「客户端 POST 一次 → 服务端持续推送」，单向足够；SSE 是普通 HTTP 响应，天然适配现有基础设施（无需额外的握手、心跳、连接管理），也让每个 API 路由保持无状态；`EventSource` 只支持 GET，无法携带请求体，所以用 `fetch` 读流并按 `\n\n` 切帧。
- **代价**：客户端→服务端没有长连接通道，因此「中断恢复」是第二个 POST 端点（`/api/agent/resume` + `Command({ resume })`），而不是在同一个连接里回话；页面关闭时服务端那一轮会跑完（浏览器行为，已在 README 标注）。
- **如果被追问**：*需要双向时怎么办？* → 真要双向（协同编辑、实时多人）才值得上 WebSocket；本项目的中断/恢复是**离散事件**，一次 POST 比维持连接更简单可靠。*SSE 的断线重连？* → 本场景不需要续传：状态由 checkpoint 承载，刷新后 `getState` 就能拿到完整状态，前端重连等于重新发一次请求。

## 11. 为什么实时数据做成图里的节点，而不是一个独立函数

- **背景**：京东实时价（`enrichLiveData`）需要「在检索之后、生成回复之前」按需补一次数据。最省事的写法是一个 `fetchLiveProduct(id)` 函数，在 `searchProducts` 或 `generateReply` 里顺手调一下。
- **选项**：① 独立函数，在节点里按需调用；② 图里的**条件触发节点**（本轮方案）。
- **决策**：做成节点，进不进由条件边判定（六条：token 已配置 / 结果非空 / 命中实时性关键词 / id 可解析 / 距上次 > 60 秒 / 当日未熔断）。
- **理由**（三条，都指向同一个结论「图是唯一编排层」）：
  1. **函数会变成图之外的特例**：谁来调、什么时候调、失败怎么办都会散落在调用点——而图里这些答案是**声明式**的（一条边 + 一个节点），读 `graph.ts` 就能看到全貌；
  2. **条件触发声明在边里可测试**：六条判定是一个纯函数（`shouldEnrich`），可以逐条构造「只差这一条」的输入断言跳过——写在函数体里就只能靠 mock 全局状态来测，且很容易漏掉某条判定的组合；
  3. **失败隔离在节点内**：节点不抛错是它的契约（失败等价于「没有实时数据」，主流程照常），因此调用点的 `try/catch` 全都消失，主流程不可能被实时数据的可用性影响。
- **代价**：多了一个节点、两个状态字段、一条条件边；演示时「节点是否触发」多了一层判定，容易出现「为什么没触发」的疑问（因此调试信息写进右栏时间线，且判定逐条有单测）。
- **如果被追问**：*为什么不在 `searchProducts` 里直接 `await` 实时价？* → 那样把「检索」与「实时补充」的职责揉在一起，`searchProducts` 会开始关心 token、配额、熔断、缓存；而且失败要么吃掉异常要么污染检索结果。*为什么不用 LangGraph 的边做「循环刷新」？* → 那会引入第二个环，环的收敛成本（refineCount 那套）要再来一遍，而实时数据只需要「一次补充」。
- **附带的一致性要求**：覆盖值必须被**落地校验**认作真实数据（`grounding.ts` 的已知金额集合要包含 `liveOverrides`），也必须进入回复上下文（`prompts.ts`）——否则会出现「回复因为实时价被判编造」或「回复报旧价、卡片报新价」两种自相矛盾。
